# 런타임 구조 위험

이 문서는 Goondan 런타임의 설계에서 지금도 손실이나 중복을 만들 수 있는 지점을 기록한다. 각 항목은 현재 코드에서 확인한 근거, 그 설계가 실제로 무너지는 상황, 손을 대야 하는 시점과 보완 방향을 담는다. 코드나 규격을 바꿀 때 해당 항목의 근거 줄을 함께 확인하고, 상태가 바뀌면 이 문서를 같은 변경에서 고친다.

## 읽는 법

| 표시 | 뜻 |
|---|---|
| 상태 `남음` | 설계가 그대로이며 시나리오가 지금도 재현된다. |
| 상태 `부분 해결` | 일부 경로는 닫혔고 남은 경로가 뒤에 적혀 있다. |
| 상태 `해결됨` | 현재 설계에서는 시나리오가 성립하지 않는다. 되돌아갈 조건을 함께 적는다. |
| 시점 `단기` | 단일 프로세스, 보통의 사용량에서도 드러난다. |
| 시점 `규모 확대 시` | 워커를 늘리거나 영속 저장소를 쓰거나 오래 띄워 둘 때 드러난다. |

아래 목록은 심각도 순이다. `해결된 위험`은 다시 논의하지 않도록 마지막에 모아 둔다.

## 남은 위험

### 1. 대화 저장소에 조건부 갱신이 없고 두 호스트 모두 대화 단위로 턴을 직렬화하지 않는다

상태 `남음` · 시점 `단기` · 범위 TypeScript, Python

근거

- `ConversationStore`는 `load`, `append`, `replace`만 가지며 버전이나 기대 개정 인수가 없다(`packages/core/src/types.ts:78`). Python 프로토콜과 기본 구현도 같다(`python/goondan/goondan/store.py:89-96`).
- 에이전트 실행은 시작할 때 대화를 한 번 읽어 자기 배열에 담고(`packages/core/src/runtime.ts:563`, `python/goondan/goondan/runtime.py:929`), `output` 단계에서 그 배열 전체로 저장소를 덮어쓴다(`packages/core/src/runtime.ts:701`과 `:1534`, `python/goondan/goondan/runtime.py:1017`).
- `runTurn`과 `run_turn`은 대화 단위 잠금을 잡지 않고, 기본 저장소에도 잠금이 없다(`packages/core/src/store.ts:9-11`).
- 규격이 대화 저장소에 요구하는 것은 (대화 식별자, 에이전트 경로) 조합의 구분과 JSON 보존뿐이며, 한 대화에서 두 턴이 겹칠 때의 규칙은 정하지 않는다(`spec/goondan.md:405-408`).

실패 시나리오

같은 대화 식별자로 웹훅 두 건이 1초 안에 도착한다. 턴 A가 빈 대화를 읽고 `user:A`를 덧붙인 뒤 모델을 기다린다. 턴 B가 `[user:A]`를 읽고 `user:B`를 덧붙인 뒤 모델을 기다린다. A의 응답이 먼저 오면 A는 자기 배열 `[user:A, assistant:A]`로 저장소 전체를 덮어쓰고 `user:B`가 사라진다. 이어서 B가 `[user:A, user:B, assistant:B]`로 덮어쓰면 `assistant:A`가 사라진다. 어느 쪽도 오류를 내지 않으며, 다음 턴의 모델은 사용자가 이미 읽은 답변이 빠진 대화를 본다. 덧붙이기만으로는 이 손실이 생기지 않는다. 오래된 읽기를 근거로 전체를 교체하는 마지막 쓰기가 원인이다.

보완 방향

두 단계로 나눈다. 먼저 두 호스트에 대화 식별자별 FIFO 잠금을 두고 턴과 완료 전달 턴을 그 안에서 실행한다. 진행 중인 대화에 들어온 입력은 병행 턴을 시작하는 대신 대기시키거나 steering으로 넘긴다. 다음으로 여러 프로세스를 쓰는 호스트를 위해 저장소 계약을 조건부로 바꾼다. `load`가 메시지와 함께 버전을 돌려주고 교체 요청이 기대 버전을 받아 불일치면 충돌을 보고하면, 런타임이 다시 읽어 자기 변경만 다시 적용할 수 있다. `output` 단계에서 전체를 덮어쓰는 대신 마지막 메시지만 식별자로 바꾸는 갱신을 쓰면 충돌 구간 자체가 좁아진다. 규격의 저장소 의무와 겹치는 두 턴을 다루는 conformance 사례를 같은 변경에서 추가한다.

### 2. 완료 전달 선점에 소유자와 만료가 없어 다른 워커의 복구가 진행 중인 전달을 회수한다

상태 `남음` · 시점 `규모 확대 시` · 범위 TypeScript, Python

근거

- 전달 선점은 `deliveryStatus`를 `pending`에서 `delivering`으로 바꿀 뿐 소유자나 만료 시각을 기록하지 않는다(`packages/core/src/types.ts:85`, `packages/core/src/store.ts:21`, `python/goondan/goondan/store.py:48-54`).
- 복구는 종료 상태이면서 `delivering`인 작업을 무조건 `pending`으로 되돌린 뒤 다시 전달한다(`packages/core/src/runtime.ts:433-436`, `spec/goondan.md:1251`).
- 예외는 같은 런타임이 진행 중인 작업뿐이다. 판별 근거가 프로세스 안의 맵이므로(`packages/core/src/runtime.ts:421`) 다른 프로세스의 전달은 구분할 수 없다. 규격도 같은 런타임만 예외로 정한다(`spec/goondan.md:1255`).
- `running` 작업도 같은 방식으로 `failed`로 전이하고 `execution_interrupted`를 기록한다(`packages/core/src/runtime.ts:427-430`, `spec/goondan.md:1250`).

실패 시나리오

워커 A와 B가 한 작업 저장소를 공유한다. A가 작업 X의 완료를 선점하고 호스트의 완료 전달 호출을 기다린다. 배포로 B가 올라와 복구를 요청하면, B는 X를 `delivering`으로 보고 `pending`으로 되돌린 뒤 다시 선점해 전달한다. 같은 완료가 두 번 전달되어 사용자는 같은 알림을 두 번 받는다. `running` 쪽은 더 나쁘다. A가 결제 도구를 실행하는 중에 B가 복구하면 작업은 `execution_interrupted`로 전달되고, A의 도구는 결제를 마친 뒤 `running`에서 `completed`로 가는 전이를 거부당한다. 에이전트는 결과를 알 수 없다고 보고하고, 사용자가 재시도하면 두 번 결제된다.

보완 방향

저장소 계약에 소유권을 넣는다. 선점은 소유자 식별자와 만료 시각을 함께 기록하고 토큰을 돌려주며, 전달 완료 기록과 반환은 그 토큰을 확인하는 조건부 갱신으로 수행한다. 복구는 만료된 선점만 회수하고, 소유자는 호스트 호출이 진행되는 동안 만료를 연장한다. `running`에도 같은 소유권을 적용해 뒤늦게 끝난 실행의 결과가 조용히 버려지는 대신 충돌로 드러나게 한다. 계약을 당장 바꾸기 어렵다면 규격과 README에 "호스트는 `deliveryId`로 중복 전달을 걸러야 한다"를 의무로 적고, 저장소를 공유하는 두 런타임을 다루는 conformance 사례를 둔다.

### 3. TypeScript는 한 대화에서 진행 중인 턴을 하나만 기억한다

상태 `남음` · 시점 `단기` · 범위 TypeScript

근거

- `#activeRuns`는 대화 식별자마다 약속 하나만 담는 맵이며(`packages/core/src/runtime.ts:214`), 새 턴이 이전 값을 덮어쓴다(`:268`). 턴이 끝날 때는 맵의 값이 자기 것일 때만 지운다(`:269`).
- 완료 전달 턴은 이 맵이 빌 때까지 기다린 뒤 시작한다(`packages/core/src/runtime.ts:1198-1204`).
- Python은 같은 자리에 실행 집합을 두고 그 대화의 모든 실행 태스크를 기다린다(`python/goondan/goondan/runtime.py:344`, `:384-387`, `:1727-1734`). 두 호스트의 동작이 여기서 갈린다.

실패 시나리오

턴 X가 진행 중일 때 턴 Y가 같은 대화에서 시작하면 맵의 값은 Y가 된다. Y가 먼저 끝나면 값이 자기 것이므로 항목을 지운다. X는 아직 모델을 기다리고 있지만 맵은 비어 있다. 이때 호스트가 승인 작업을 승인하면 완료 전달 턴이 기다리지 않고 바로 시작해 완료 입력과 에이전트의 반응을 대화에 덧붙이고, 작업은 `delivered`로 기록된다(`packages/core/src/runtime.ts:1187`). 뒤이어 X가 `output` 단계에서 자기 배열로 대화를 덮어쓰면 그 두 메시지가 사라진다. 작업은 `delivered`로 남고 대화에는 그 완료의 흔적이 없다.

보완 방향

`#activeRuns`를 대화별 집합으로 바꾸고 각 턴이 자기 항목만 지우게 하여 Python과 맞춘다. 위험 1의 대화별 FIFO 잠금을 도입하면 이 추적기 자체가 필요 없어지므로, 잠금을 먼저 넣고 추적기를 걷어내는 순서가 낫다.

### 4. 모델 호출 상한에 기본값이 없고 중첩 실행 깊이에는 상한 자체가 없다

상태 `부분 해결` · 시점 `단기` · 범위 TypeScript, Python

근거

- `maxSteps`는 선택이며 지정하지 않으면 상한이 없다(`packages/core/src/types.ts:117-118`, `python/goondan/goondan/runtime.py:322`, `spec/goondan.md:1009`). 지정하면 두 호스트가 같은 지점에서 실행 오류로 멈춘다(`packages/core/src/runtime.ts:643-646`, `python/goondan/goondan/runtime.py:980-981`).
- `maxRetries`는 두 호스트에서 기본값 3이며 `error` 재시도와 `modelResult` 재시도를 합해 센다(`packages/core/src/runtime.ts:735`과 `:1360`, `python/goondan/goondan/runtime.py:652-653`, `spec/goondan.md:1951`). 무한 재시도 경로는 닫혔다.
- 상한과 재시도는 에이전트 실행마다 따로 세며 하위 실행은 자기 예산을 새로 받는다(`spec/goondan.md:1009`, `:1951`). 중첩 깊이를 세는 값은 두 호스트 어디에도 없다.
- 훅 컨텍스트의 `model.run`은 상한에 포함하지 않는다(`spec/goondan.md:1009`). 다만 이 호출은 `modelInput` 훅을 다시 타지 않으므로(`packages/core/src/runtime.ts:1514-1518`) 훅이 자기 자신을 다시 부르는 경로는 없다.

실패 시나리오

에이전트 A가 자신을 에이전트 도구로 선언하면 각 실행이 자기 예산으로 A를 다시 호출한다. `maxSteps: 2`를 지정해도 깊이는 제한되지 않으므로 호출이 계속 늘어나고, 프로세스가 스택이나 메모리를 소진할 때까지 유료 모델을 호출한다. 상한을 아예 지정하지 않은 호스트에서는 프롬프트 주입이 담긴 웹 페이지를 읽은 에이전트가 매 단계 도구 호출을 내보내며 누군가 프로세스를 죽일 때까지 같은 일을 반복한다.

보완 방향

규격에 턴 예산을 정의한다. 실행마다 따로 세는 현재 규칙은 유지하되 턴 전체에 적용되는 중첩 깊이 상한을 추가하고, 하위 실행에 남은 깊이를 전달한다. `maxSteps`에 무한이 아닌 기본값을 줄지는 호환성 결정이 필요하다. 기본값을 두지 않기로 한다면 README와 규격에 "상한을 지정하지 않은 호스트는 모델 호출 횟수에 상한이 없다"를 명시하고 CLI가 기본값을 지정하도록 한다. 두 호스트가 같은 단계에서 같은 오류로 멈추는지는 conformance 사례로 고정한다.

### 5. 확장 인스턴스 캐시가 확인과 저장 사이에서 갈린다

상태 `남음` · 시점 `단기` · 범위 TypeScript, Python

근거

캐시를 확인한 뒤 확장을 만드는 `await`를 거치고 나서야 맵에 넣는다(`packages/core/src/runtime.ts:840`과 `:868`, `python/goondan/goondan/runtime.py:443`과 `:470`). 인스턴스는 런타임을 닫을 때만 정리된다(`packages/core/src/runtime.ts:476`, `python/goondan/goondan/runtime.py:1748`).

실패 시나리오

재시작 직후 같은 대화로 메시지 두 건이 함께 도착한다. 두 실행 모두 캐시가 비어 있는 것을 보고, 벡터 DB 연결을 여는 확장을 각각 만든다. 뒤에 저장한 인스턴스가 앞의 것을 덮어쓰므로 첫 실행은 자기 실행 내내 버려진 인스턴스를 쓰고 이후 턴은 다른 인스턴스를 쓴다. 확장이 메모리에 들고 있는 상태는 둘로 갈리고, 런타임을 닫을 때는 맵에 남은 하나만 정리되므로 첫 연결은 프로세스가 끝날 때까지 남는다.

보완 방향

완성된 인스턴스 대신 만들고 있는 약속을 캐시에 넣는다. TypeScript는 `Promise`를, Python은 `asyncio.Task`를 `await` 앞에서 저장하고 실패하면 항목을 지운다. 그러면 동시에 들어온 호출이 같은 인스턴스를 공유한다.

### 6. 대화를 끝내는 API가 없어 대화 단위 상태가 종료 시점까지 쌓인다

상태 `남음` · 시점 `규모 확대 시` · 범위 TypeScript, Python

근거

- (대화 식별자, 에이전트 경로)마다 확장 인스턴스와 비동기 훅 기록을 보관하며, 런타임을 닫을 때까지 어느 항목도 지우지 않는다(`packages/core/src/runtime.ts:201-202`, `:476-477`, `:824-825`, `python/goondan/goondan/runtime.py:335`, `:1748`).
- 에이전트 도구의 하위 실행은 부모 턴마다 새 대화 식별자를 받으므로(`packages/core/src/runtime.ts:973`) 부모 턴 하나마다 인스턴스 묶음이 하나씩 더 남는다.
- 기본 저장소는 아무것도 지우지 않으며(`packages/core/src/store.ts:15`, `python/goondan/goondan/store.py:27`) 복구는 저장소의 모든 작업을 조회한다(`packages/core/src/runtime.ts:419`).
- 런타임을 닫을 때 Python은 완료 전달 태스크를 취소하지만(`python/goondan/goondan/runtime.py:1746`) TypeScript는 호스트의 완료 전달 호출에 중단 신호를 주지 않는다(`packages/core/src/runtime.ts:467-478`, `:1185`).

닫을 때의 차이는 저장소 상태로는 드러나지 않는다. 규격은 닫은 뒤 끝난 전달을 기록하지 않도록 정하고 두 호스트가 이를 지킨다(`spec/goondan.md:1261`, `packages/core/src/runtime.ts:1190`). 드러나는 곳은 종료 시간이다. TypeScript에서는 호스트의 완료 전달 호출이 끝날 때까지 `idle()`이 돌아오지 않으므로, 응답이 느린 전달 대상이 있으면 종료가 그만큼 늦어진다.

실패 시나리오

하루에 수천 대화를 처리하는 채팅 서버가 런타임 하나를 계속 쓴다. 대화마다, 그리고 에이전트 도구 호출마다 확장 인스턴스가 남고 그 안의 DB 연결과 타이머도 함께 남는다. 메모리 사용량은 누적 트래픽에 비례해 늘어나며 동시 처리량을 줄여도 내려가지 않는다. 복구를 호출할 때마다 이미 전달을 마친 작업까지 전부 조회한다.

보완 방향

대화 수명 API를 추가한다. 대화 하나를 지정해 그 대화의 확장 인스턴스를 정리하고 대기 중인 훅 기록을 버리는 요청을 두고, 선택적으로 LRU나 TTL 제거를 제공한다. 부모 턴이 끝나면 에이전트 도구 하위 실행의 인스턴스는 바로 정리한다. 규격은 이미 다음 부모 턴이 새 하위 대화를 시작한다고 정하므로 의미가 바뀌지 않는다. 작업 저장소에는 전달을 마친 작업을 정리하는 방법을 규격에 정하거나, 최소한 복구가 이미 전달을 마친 작업을 조회 대상에서 빼도록 한다.

### 7. 저장 레코드에 스키마 버전과 이관 절차가 없다

상태 `남음` · 시점 `규모 확대 시` · 범위 TypeScript, Python

근거

- 구성 문서에는 `version`이 있지만(`spec/goondan.md:153`) 저장되는 메시지와 작업 레코드에는 버전 필드가 없다(`packages/core/src/types.ts:13`, `:83`). 기본 저장소는 값을 검증 없이 그대로 쓰고 읽는다(`packages/core/src/store.ts:9-22`, `python/goondan/goondan/store.py:89-96`).
- 복구는 필드 값에 그대로 의존한다. `deliveryStatus`가 없는 레코드는 복구 표의 어느 행에도 맞지 않아 전달을 시작하지만(`packages/core/src/runtime.ts:432-436`), 선점은 `deliveryStatus`가 `pending`일 때만 성공하므로(`packages/core/src/store.ts:21`, `python/goondan/goondan/store.py:52`) 아무 일도 하지 않고 조용히 끝난다.
- 규격에 레코드 이관 절차가 없다.

실패 시나리오

Postgres 기반 작업 저장소를 쓰는 팀이 작업 레코드의 필드 구성을 바꾸는 릴리스를 배포한다. 배포 이후 복구는 업그레이드 이전에 만들어진 승인 작업을 로그 한 줄 없이 건너뛴다. 사용자는 승인한 작업의 완료 알림을 받지 못하고, 운영자는 저장소에 남은 레코드만 보고 원인을 찾지 못한다. 메시지 쪽은 더 눈에 띈다. 형식이 다른 메시지가 섞인 대화는 매 턴 단계 값 검사에서 실패하므로 그 대화를 이어 갈 수 없다.

보완 방향

저장하는 메시지와 작업 레코드에 스키마 버전을 넣고, 규격 옆에 저장 레코드용 JSON 스키마를 둔다. 읽을 때 타입 검사기로 해석하고 버전별 이관 함수를 거치게 한다. 복구는 모르는 형식과 빠진 필드를 조용히 넘기는 대신 명시적인 기본값을 적용하거나 오류로 보고한다. 이전 버전 레코드를 읽는 conformance 사례를 둔다.

### 8. 두 호스트의 작업 저장소 프로토콜이 다르다

상태 `남음` · 시점 `규모 확대 시` · 범위 TypeScript, Python

근거

- TypeScript는 `claimDelivery(conversationId, operationId, updatedAt)`와 `releaseDelivery(conversationId, operationId, deliveryId, updatedAt)`를 요구하고, 전달 완료는 `transition`으로 기록한다(`packages/core/src/types.ts:85`, `packages/core/src/runtime.ts:1187`).
- Python은 `claim_delivery(conversation_id, operation_id)`와 `release_delivery(conversation_id, operation_id)`에 더해 별도의 `finish_delivery(...)`를 쓰고 `updatedAt`을 저장소가 직접 채운다(`python/goondan/goondan/store.py:48-75`, `python/goondan/goondan/runtime.py:1713`).
- 규격은 조건부 전이와 전달 선점의 원자성만 정하고 요청 구성은 정하지 않는다(`spec/goondan.md:1166`).

실패 시나리오

두 언어의 호스트를 함께 운영하는 팀이 영속 작업 저장소를 하나 구현한다. TypeScript용으로 만든 어댑터에는 `finish_delivery`가 없으므로 Python 런타임은 전달을 끝내지 못하고, 반대로 Python용으로 만든 어댑터의 반환 요청은 `deliveryId`를 확인하지 않으므로 다른 런타임의 선점을 회수한다. 저장소 하나를 두 호스트가 함께 쓰는 배치는 지금 불가능하다.

보완 방향

규격에 작업 저장소가 제공해야 하는 요청 목록과 각 요청의 인수, 원자성 조건을 언어 중립으로 적고 두 호스트를 그 목록에 맞춘다. 위험 2의 소유권 도입과 같은 변경에서 처리하는 편이 낫다.

### 9. 이벤트에 실행을 잇는 식별자가 없다

상태 `남음` · 시점 `규모 확대 시` · 범위 TypeScript, Python

근거

- 이벤트는 `{name, agent, conversationId, turnId, at, data}`만 가진다(`packages/core/src/types.ts:139`). Python도 같은 봉투를 만들며 시각을 포함한다(`python/goondan/goondan/runtime.py:502`).
- 하위 실행은 파생 대화 식별자와 새 턴 식별자를 받을 뿐 부모를 가리키는 필드가 없다(`packages/core/src/runtime.ts:973`, `:1490`, `spec/goondan.md:417`).
- 승인 작업의 실행과 완료 전달은 턴 이벤트를 알리지 않으며 작업 식별자로만 이어진다(`spec/goondan.md:1212`).

실패 시나리오

비용이 갑자기 늘어 당직자가 조사한다. 이벤트에는 `c1`, `c1:<턴 식별자>:worker`, `c1:main:modelInput:advisors/left` 같은 대화 식별자와 서로 다른 턴 식별자가 보이지만, 어느 사용자 요청이 이 실행들을 낳았는지 이어 줄 필드가 없다. 문자열 규칙에서 부모를 되짚어야 하고, 훅 에이전트와 승인 작업 실행은 그 규칙으로도 원래 턴에 닿지 않는다. 두 언어로 나눠 운영하는 팀은 대시보드 하나로 두 호스트를 볼 수도 없다.

보완 방향

이벤트 봉투에 실행 식별자, 부모 실행 식별자, 턴 전체를 묶는 추적 식별자와 깊이를 추가한다. 승인 작업 관련 이벤트에는 작업 식별자와 작업을 만든 턴의 식별자를 함께 넣는다. 값은 하위 실행 옵션으로 전파한다. W3C `traceparent`와 맞출 수 있는 형식을 고르면 호스트가 기존 추적 백엔드에 그대로 흘려보낼 수 있다. 봉투를 규격에 적고 두 호스트가 같은 키를 내보내는지 conformance 사례로 고정한다.

### 10. 훅 컨텍스트의 규격 밖 멤버가 두 호스트에서 다르다

상태 `남음` · 시점 `단기` · 범위 TypeScript, Python

근거

TypeScript 훅 컨텍스트에는 규격에 없는 `step`과 `log`가 있다(`packages/core/src/types.ts:97`). Python 훅 컨텍스트에는 그 둘이 없고 대신 `source`, `local`, `phase`, `hook`, `detached`, `run_state`가 있다(`python/goondan/goondan/types.py:265-280`). 규격의 훅 컨텍스트 표에는 어느 쪽도 없다.

실패 시나리오

TypeScript용으로 만든 확장을 Python으로 옮긴 팀이 훅 안에서 `ctx.log.info(...)`를 호출한다. 구성 검증은 그대로 통과하고 턴이 실행되는 중에 속성 오류가 난다. 오류는 훅 실패로 보고되므로 원인이 확장 이식이라는 사실이 로그에 드러나지 않는다.

보완 방향

각 멤버를 규격에 넣어 두 호스트에 구현하거나 삭제한다. 확장 정의의 생성 입력은 이미 로거를 받으므로 훅 컨텍스트의 로거는 규격에 넣을 근거가 있고, `step`은 실행 내부 값이라 판단이 다르다. 남기기로 한 멤버는 규격의 훅 컨텍스트 표에 적고, 두 호스트의 공개 표면을 비교하는 검사를 CI에 둔다.

### 11. 템플릿이 읽을 수 있는 파일 범위는 구성 작성자를 신뢰하는 전제 위에 있다

상태 `부분 해결` · 시점 `단기` · 범위 TypeScript, Python

근거

- 템플릿 엔진을 통한 탈출은 닫혔다. TypeScript 렌더러는 파일 시스템에 접근하지 않고 미리 읽은 맵만 쓰며, 허용 목록으로 검사한 구문 트리를 직접 평가한다(`packages/core/src/template.ts:10-12`, `:28-34`). Python 환경은 속성 읽기와 키 읽기를 JSON 읽기로 덮어써 호스트 속성과 메서드에 닿지 못하게 하고(`python/goondan/goondan/template.py:620-638`), 로더는 미리 읽은 맵이며(`:571`) `include` 경로에서 절대 경로와 `..`를 거부한다(`:149-153`).
- 남은 것은 YAML이 선언한 경로다. 규격은 선언한 경로에 위치 제한을 두지 않고 절대 경로와 `..`를 허용한다(`spec/goondan.md:143`).

실패 시나리오

고객이 자기 `goondan.yaml`과 템플릿을 올리는 플랫폼에서는 구성 작성자와 호스트 운영자가 다르다. 고객이 `systemMessage.template`에 `/app/.env`를 적으면 호스트의 자격 증명이 시스템 프롬프트에 들어가고 모델이 그대로 되돌려 준다.

보완 방향

이 범위는 규격이 정한 결정이므로 문서에서 다룬다. README와 규격에 "구성 작성자는 호스트 프로세스가 읽을 수 있는 파일을 읽을 수 있다"를 신뢰 경계로 적고, 구성 작성자를 신뢰할 수 없는 호스트는 구성을 읽기 전에 경로를 직접 제한하거나 별도 프로세스로 격리하도록 안내한다. 런타임에 경로 제한을 넣는다면 호스트가 켜는 선택 기능이어야 한다. 기본값을 바꾸면 절대 경로를 쓰는 기존 구성이 깨진다.
