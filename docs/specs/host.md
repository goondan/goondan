# 호스트와 코드 로딩

Goondan의 TypeScript 런타임은 호스트의 Node 프로세스 안에서 실행합니다. Python 런타임은 Python 호스트 프로세스 안에서 실행합니다. 에이전트 실행과 인라인 에이전트 호출은 각 프로세스 안의 비동기 작업입니다. CLI의 `bash`처럼 호스트 도구가 외부 프로그램을 실행할 때에는 해당 도구가 자식 프로세스를 만듭니다.

## 구성과 구현의 연결

호스트가 모델·도구·함수·확장 구현을 import한 뒤 이름별 바인딩을 런타임에 전달합니다. YAML의 `model`, `tool`, `fn`과 `extensions` 키는 이 등록 이름을 참조합니다. `template`은 텍스트 파일 경로이고 에이전트의 `config`는 다른 Goondan 구성 경로입니다.

`gdn run --bindings ./bindings.mjs`와 `gdn chat --bindings ./bindings.mjs`는 지정한 모듈의 `bindings` 또는 default export를 읽습니다. 모듈 경로는 명령을 실행한 디렉터리를 기준으로 절대 파일 URL로 변환하며, Node의 ESM 로더가 import와 캐시를 소유합니다. 런타임은 에이전트를 실행할 때마다 이 모듈을 다시 import하지 않습니다. TypeScript 소스 파일을 직접 지정하려면 사용하는 Node 환경에 TypeScript 실행 지원이 필요합니다. 컴파일한 `.mjs`·`.js` 바인딩은 일반 ESM 모듈로 실행합니다.

Python 호스트는 `import goondan`과 일반 Python import로 바인딩을 등록합니다. 모듈 캐시는 Python이 소유합니다. TypeScript와 Python 간 통신이 필요한 제품에서는 호스트가 명시적인 프로세스·RPC 도구를 구현합니다. 기본 CLI의 바인딩 모듈은 Node에서 실행합니다.

## 번들 배포

호스트를 번들로 배포할 때에는 구현 코드를 호스트 진입점에서 import하고, YAML과 템플릿은 읽을 수 있는 자산으로 함께 배포합니다. 구성 파일 사이의 상대 디렉터리 관계를 유지하고 배포된 구성 경로를 `loadConfig`에 전달합니다. 로더는 각 파일이 선언한 템플릿과 중첩 구성 경로를 해당 파일 기준으로 해석합니다.

바인딩 구현을 번들에 포함할지 외부 모듈로 로드할지는 호스트 빌드가 결정합니다. 같은 구현을 번들 내부 코드와 별도 바인딩 모듈 양쪽에 포함하면 두 복사본이 생길 수 있으므로, 공유 상태가 있는 구현은 한 진입점에서 생성해 바인딩으로 전달합니다. Goondan은 YAML을 근거로 구현 코드를 별도 로딩하지 않습니다.

확장 구현 모듈과 확장 인스턴스는 수명이 다릅니다. 모듈을 한 번 import해도 `create`는 에이전트와 대화의 조합마다 호출됩니다. 같은 조합에서 다음 턴을 실행하면 인스턴스를 재사용하고, `close`에서 정리합니다. 공유 서비스와 영속 상태는 호스트가 포트·저장소로 제공하고 확장은 자신의 대화 상태를 관리합니다.
